## Executive summary

LedgerLens remains a local demonstration, not a production AP system. This pass added a durable `ProcessingOutbox` that commits with invoice/job state; bounded retry/backoff and claim fencing; safe exhaustion handling, admin-only inspection/retry with an audit reason, and UI visibility. The source remains saved and the job remains queued during recoverable dispatch failures; only retry exhaustion transitions it to a dispatch-stage failure/human-review case. Idempotent replay retains the original invoice/job and does not bypass backoff or resend a published event.

Reconciliation now checks cumulative prior invoice quantity by PO line using latest stored match details and excludes rejected/cancelled/voided invoices. Partial-invoice tax expectation is based on that invoice's quantity. Closed/cancelled POs and freight/discount amounts without a PO allowance are explicitly surfaced as exceptions/manual review. Existing human review and no-payment semantics are preserved.

An opt-in local token-classifier adapter is available for a future approved fine-tuned checkpoint. It is disabled by default, uses local-only artifacts, preserves deterministic fallback evidence, and forces human validation of accepted candidates. **No checkpoint, labeled corpus, inference accuracy, or pretrained-model capability is supplied or claimed.**

This pass also added an optional generic REST ERP sandbox connector for read-only vendor/PO/GRN reference imports, transactional collision-safe persistence, an admin sync control, and a separate provider-reported invoice-status lookup. The status result is not persisted or allowed to change workflow. A local extraction-evaluation CLI accepts operator-supplied labeled JSONL. Both additions are tested against synthetic fixtures / HTTPX mock transport only; no external provider or document corpus was used.

The current extension added a generic signed raw-RFC822 attachment webhook (not a mailbox/provider integration), with bounded attachment validation, event idempotency, the existing processing outbox, and an additive migration. Admins can export correction pairs explicitly approved after resolved human review; this is audited dataset preparation only, not model training. Optional local-only duplicate embeddings add an uncalibrated review signal when a caller supplies an approved checkpoint; no weights are bundled and failures fall back to deterministic checks.

## Residual findings and operational limits

1. **No production tenant boundary.** Users share one database workspace; route-level roles are not tenant isolation. Do not deploy as a multi-customer service without tenant IDs, scoping, migration/backfill, and cross-tenant tests.
2. **Filesystem/database are not atomic.** A hard crash during upload can leave an orphan file. The bounded admin storage check is read-only; it does not adopt, repair, or delete anything.
3. **Processing crashes after job claim are still manual.** Outbox persists dispatch intent; if a worker claims a job and dies while `processing`, stale recovery is admin-only and does not retry automatically. Long OCR stages do not heartbeat periodically.
4. **At-least-once delivery.** Claims and worker state fence duplicates but do not provide exactly-once delivery. No live PostgreSQL/Celery acknowledgement-loss or multi-host test was run.
5. **Extraction/model performance is unknown.** Default extraction is deterministic rules plus local OCR. No real labeled invoice corpus, trained layout artifact, >98% accuracy evidence, fraud precision/recall, calibration, ROI, or avoided-loss proof is available.
6. **Finance domain configuration is partial.** There is no FX conversion, tax/legal advice, live provider-specific procurement sync, or PO freight allowance model. The generic ERP sandbox adapter has not been tested against a real service. Freight/discount amounts without a PO term are held for human review.
7. **Security/production controls are incomplete.** Per-session revocation/rotation is now implemented and locally tested, but bearer tokens remain in `localStorage`; a failed logout request can leave that server session usable until expiry, and there is no session listing/revoke-all operator control. Local Python/npm dependency audits reported no known vulnerabilities; the Trivy source-secret and container-image scans are configured but have not run. Distributed rate limits, external SSO/MFA, tenant boundary, WORM audit storage, secret manager/key rotation, production backup/restore exercise, live malware scan, independent security review, and target-environment load test remain unverified or absent.
8. **No live external provider or payments.** A generic mock-tested ERP reference import and read-only invoice-status lookup exist, but there is no authorized ERP sandbox/provider or production credential. A generic signed email webhook is implemented and locally tested, but no mailbox/provider is connected and upstream sender authenticity must be verified before forwarding. Cloud OCR, bank validation, payment execution, generative contract, and blockchain features remain absent. A match/reviewer/provider-reported state must not be interpreted as payment authorization.
9. **Deployment/E2E are unverified.** Compose and Docker were not run; only isolated synthetic-data Chromium E2E was available, with no hosted browser run, PostgreSQL, Redis/Celery, or production service. Synthetic tests and configuration are not evidence of deployment success.
